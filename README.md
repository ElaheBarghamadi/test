# سامانه آزمون غیرحضوری

سامانه مدیریت و برگزاری آزمون آنلاین (معلم / دانش‌آموز / مدیر) با جنگو.

---

## 🚀 اجرای پروژه روی دستگاه خودتان (حالت توسعه)

### پیش‌نیاز
- پایتون **3.11 یا جدیدتر** ([python.org](https://www.python.org/downloads/))
- در ویندوز هنگام نصب، تیک **Add Python to PATH** را بزنید.

### ۱) دریافت کد
```bash
git clone https://github.com/ElaheBarghamadi/test.git
cd test
```

### ۲) ساخت محیط مجازی و نصب وابستگی‌ها
**ویندوز (CMD یا PowerShell):**
```bat
py -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```
**لینوکس / مک:**
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### ۳) ساخت دیتابیس
```bash
python manage.py migrate
```

### ۴) داده نمونه (اختیاری ولی توصیه‌شده)
```bash
python manage.py seed_demo
```
این دستور کاربرها و دو آزمون کامل (با همه انواع سوال و تصویر) می‌سازد:

| نقش | نام کاربری | رمز |
|---|---|---|
| مدیر | `admin_t` | `test12345` |
| معلم | `teacher_t` | `test12345` |
| دانش‌آموز | `student_t1` (و `student_t2`, `student_t3`) | `test12345` |

### ۴.۵) کاربران پیش‌فرض (خودکار)
با هر بار اجرای `runserver` (یا دستی با `python create_default_users.py` / `python manage.py ensure_default_users`)
این سه کاربر **اگر وجود نداشته باشند** ساخته می‌شوند (رمز = نام کاربری):

| نقش | نام کاربری | رمز |
|---|---|---|
| مدیر اصلی | `admin` | `admin` |
| معلم | `teacher` | `teacher` |
| دانش‌آموز | `student` | `student` |

> ⚠️ در سرور واقعی حتماً رمز این کاربران را عوض کنید.

### ۴.۶) بانک سوال نمونه (پوشه‌بندی‌شده)
```bash
python manage.py seed_question_bank                # برای معلم teacher
python manage.py seed_question_bank --teacher ali  # برای معلم دیگر
python manage.py seed_question_bank --all          # برای همهٔ معلم‌ها
python manage.py seed_question_bank --reset        # پاک‌کردن بانک معلم و ساخت دوباره
```
حدود ۹۴ سوال از همهٔ انواع در ساختار «پایه › درس › فصل». معلم می‌تواند از دکمهٔ
«✨ بارگذاری بانک نمونه» در صفحهٔ بانک سوال هم همین کار را انجام دهد. اجرای دوباره سوال تکراری نمی‌سازد.

### ۵) اجرای سرور
```bash
python manage.py runserver
```
سپس مرورگر: <http://127.0.0.1:8000/>

> 💡 حالت توسعه به‌صورت خودکار فعال می‌شود: چون با `runserver` اجرا کرده‌اید،
> `DEBUG=True` در نظر گرفته می‌شود.
> فایل‌های استاتیک و رسانه همین‌طور سرو می‌شوند و ریدایرکت HTTPS اتفاق نمی‌افتد.

## 👤 کاربران پیش‌فرض

کاربران `admin/admin`، `teacher/teacher` و `student/student` به‌طور خودکار ساخته می‌شوند (اگر نباشند):
بعد از هر `python manage.py migrate`، با `runserver`، و هنگام بالا آمدن سرور تولید (gunicorn) —
پس روی Render و هاست‌هایی که دیتابیس با هر deploy پاک می‌شود هم همیشه وجود دارند.
دستی: `python manage.py ensure_default_users` (به رمز کاربران موجود دست نمی‌زند).

## 🔧 تنظیمات

همهٔ مقدارهای حساس از **متغیرهای محیطی** خوانده می‌شوند تا هیچ رازی داخل مخزن نماند.

### متغیرهای محیطی

| متغیر | لازم در تولید؟ | پیش‌فرض | توضیح |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | ✅ **بله** | — (بدون آن برنامه بالا نمی‌آید) | کلید امضا. ساخت: `python -c "import secrets;print(secrets.token_urlsafe(50))"` |
| `DJANGO_ALLOWED_HOSTS` | توصیه می‌شود | `.onrender.com,localhost,127.0.0.1` | فهرست جداشده با کاما. نقطهٔ آغازین = همهٔ زیردامنه‌ها |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | در صورت دامنهٔ دیگر | onrender.com، e2b.app، localhost | فهرست جداشده با کاما |
| `DJANGO_HTTPS_ONLY` | نه | **`true` در تولید** / `false` در توسعه | کوکی Secure + ریدایرکت HTTPS + HSTS |
| `DJANGO_HSTS_SECONDS` | نه | `31536000` (یک سال) | عمر HSTS |
| `DJANGO_HSTS_INCLUDE_SUBDOMAINS` | نه | `true` | شامل زیردامنه‌ها |
| `DJANGO_HSTS_PRELOAD` | نه | `false` | ⚠️ برگشت‌ناپذیر است؛ فقط وقتی مطمئنید `true` کنید |
| `DJANGO_ENV` | نه | استنتاج می‌شود | `production` یا `development` برای override صریح |
| `DJANGO_DEBUG` | نه | استنتاج می‌شود | `1`/`0` برای override صریح |
| `REDIS_URL` | نه | کش درون‌حافظه | برای rate-limit مشترک بین چند worker |
| `TRUSTED_PROXY_COUNT` | نه | `0` | فقط پشت reverse proxy مطمئن |

### تشخیص خودکار توسعه / تولید

| نحوهٔ اجرا | `DEBUG` | `IS_PRODUCTION` |
|---|---|---|
| `python manage.py runserver` | `True` | `False` |
| `python manage.py test` / `migrate` / `check` / `collectstatic` | `False` | `False` |
| `gunicorn` / `uwsgi` (WSGI واقعی) | `False` | **`True`** |

در حالت تولید، **نبودِ `DJANGO_SECRET_KEY` باعث شکست عمدی (fail-fast) می‌شود** تا هرگز
با کلیدِ عمومی بالا نیایید. در توسعه یک کلید مشخصاً «dev-only» استفاده می‌شود.

سایر تنظیمات:

| تنظیم | مقدار فعلی |
|---|---|
| `DATABASES` | sqlite فایل `db.sqlite3` |
| `LOGIN_URL` | `login` → `/login/` (پیش‌تر تنظیم نشده بود و به `/accounts/login/` می‌رفت که ۴۰۴ است) |

## 🌐 اجرای تولید (Production)

```bash
export DJANGO_SECRET_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(50))')"
export DJANGO_ALLOWED_HOSTS="example.com,www.example.com"
export DJANGO_CSRF_TRUSTED_ORIGINS="https://example.com"

python manage.py migrate
python manage.py collectstatic --noinput
gunicorn exam_system.wsgi:application --bind 0.0.0.0:8000
```
در حالت تولید به‌صورت پیش‌فرض: کوکی‌ها `Secure` می‌شوند، ریدایرکت HTTPS و HSTS فعال است،
`ALLOWED_HOSTS` محدود است و فایل‌های استاتیک با WhiteNoise سرو می‌شوند
(پوشه `staticfiles/` توسط `collectstatic` ساخته می‌شود).
فایل‌های آپلودشده (`media/`) فقط از مسیر محافظت‌شده `/media/` و با احراز دسترسی سرو می‌شوند.

### بررسی سلامت استقرار
```bash
DJANGO_ENV=production DJANGO_SECRET_KEY=... DJANGO_ALLOWED_HOSTS=... \
  python manage.py check --deploy
```
باید `System check identified no issues` بدهد.

> ⚠️ اگر سایت شما واقعاً روی **http** سرو می‌شود (پشت HTTPS نیست)،
> `DJANGO_HTTPS_ONLY=0` بگذارید؛ وگرنه کوکی ورود ارسال نمی‌شود و لاگین کار نمی‌کند.

## ❓ خطاهای رایج

| خطا | علت و راه‌حل |
|---|---|
| `You're accessing the development server over HTTPS...` + ریدایرکت 301 | سرور توسعه با `DEBUG=False` اجرا شده. با `runserver` این حالت خودکار رفع می‌شود؛ در غیر این صورت `set DEBUG=True` بزنید. |
| `UserWarning: No directory at: .../staticfiles/` | فقط در حالت تولید معنا دارد؛ `collectstatic --noinput` اجرا کنید. در توسعه این هشدار ظاهر نمی‌شود. |

## ✨ قابلیت‌های اضافه‌شده (نسخه ۲٫۰)

### ۱) فوتر جدید، مدرن و کاملاً ریسپانسیو
- قالب مشترک: `templates/_footer.html` + استایل‌ها در `static/css/layout.css` (لایهٔ نهایی در `spacing.css`)
- چهار ستون: برند و توضیح سامانه، دسترسی سریع (بر اساس نقش کاربر)، راهنما و قوانین (مودال داخلی)، پشتیبانی و وضعیت سامانه
- در موبایل ستون‌ها به **آکاردئون** تبدیل می‌شوند؛ نوار پایینی تیره با نسخه، نام کاربر جاری و دکمهٔ بازگشت به بالا
- سازگار با `prefers-reduced-motion`، حالت چاپ و `safe-area` موبایل

### ۲) پنل دانش‌آموز: مرکز اطلاعیه‌ها
- بخش اطلاعیه‌ها به بالای داشبورد منتقل شد: نشان «جدید»، مخاطب (پایه/همه)، نویسنده، تاریخ شمسی و متن بازشونده
- «علامت همه به‌عنوان خوانده‌شده» (ذخیره در نشست کاربر) و شمارندهٔ خوانده‌نشده در هدر و منو
- زنگولهٔ هدر بازطراحی شد با سربرگ، فهرست اسکرول‌شونده و دکمهٔ «مشاهدهٔ همه»

### ۳) صفحهٔ یکپارچهٔ نتایج: `/student/results/`
- همهٔ آزمون‌ها (ثبت‌شده، نیمه‌تمام، شروع‌نشده) + نتایج منتشرشده در یک جدول
- حلقهٔ معدل از ۲۰، میانگین درصد، بهترین/نیازمند تقویت، شمارش قبولی‌ها
- فیلتر وضعیت، جستجو، مرتب‌سازی و **ریزنمرات هر سوال** در ردیف بازشو
- در موبایل جدول به کارت تبدیل می‌شود؛ دکمهٔ چاپ کارنامه

### ۴) پنل ادمین: صفحهٔ «جزئیات کاربر» (`/admin-panel/users/<id>/`)
- با کلیک روی نام هر کاربر در «مدیریت کاربران» باز می‌شود
- چهار تب: مشخصات | نشست‌ها و دستگاه‌ها | فعالیت | امنیت
  - **مشخصات:** هویت، نقش، پایه، کد دانش‌آموزی، وضعیت حساب، تاریخ عضویت/آخرین ورود/آخرین فعالیت، بازنشانی رمز
  - **نشست‌ها:** نشست‌های ورود فعال با زمان باقی‌مانده + پایان همهٔ نشست‌ها، نشست‌های آزمون با IP و User-Agent، دستگاه‌ها و آی‌پی‌های یکتا
  - **فعالیت:** آزمون‌ها و نمره‌ها (دانش‌آموز) یا آزمون‌های ساخته‌شده (معلم)، رفتارهای مشکوک، لاگ فعالیت
  - **امنیت:** ارزیابی ریسک (پایین/متوسط/بالا)، شمارنده‌ها و تایم‌لاین رویدادهای امنیتی
- مدل جدید `admin_panel.SecurityEvent`: ثبت ورود موفق/ناموفق، قفل حساب، خروج، بازنشانی رمز، ویرایش توسط مدیر، پایان نشست و…
  - رویدادها به‌صورت خودکار در `accounts/views.py` (ورود/خروج/قفل) و اکشن‌های ادمین ثبت می‌شوند
  - تجزیه‌گر User-Agent داخلی (`parse_user_agent`) بدون وابستگی بیرونی: مرورگر، سیستم‌عامل، نوع دستگاه
- اکشن‌های مدیر: `user_terminate_sessions`، `user_toggle_active`، `user_reset_password`

### ۵) تکمیل صفحهٔ جزئیات کاربر (نسخهٔ کامل)
- **تب نشست‌ها و دستگاه‌ها:** هر نشست ورود فعال با مرورگر/سیستم‌عامل/نوع دستگاه، آی‌پی، زمان ورود و اعتبار باقی‌مانده؛ جدول دستگاه‌های یکتا و آی‌پی‌های یکتا با تعداد رویداد + اولین/آخرین مشاهده و منبع (ورود/آزمون)
- **تب امنیت:** تاریخچهٔ ورود/خروج (موفق/ناموفق با آی‌پی و دستگاه)، تایم‌لاین «کنش‌های مدیریتی روی این حساب» (ساخت، ویرایش، بازنشانی رمز، پایان نشست، فعال/غیرفعال — با نام مدیرِ انجام‌دهنده)، و همهٔ رویدادهای امنیتی
- **تب مشخصات:** آخرین ورود با آی‌پی و دستگاه دقیق
- هر کنش مدیر روی یک کاربر، هم در کارنامهٔ خود مدیر و هم در پروندهٔ کاربر مقصد ثبت می‌شود
- لینک به جزئیات کاربر از: مدیریت کاربران، داشبورد ادمین (آخرین کاربران)، جزئیات آزمون (دانش‌آموزان مجاز) و تحلیل دانش‌آموزان

## 🔒 لایهٔ امنیت و اعتبارسنجی ورودی‌ها (`core/security.py`)

### اصل: هیچ دادهٔ کاربر بدون پاک‌سازی ذخیره نمی‌شود
- `clean_text`: حذف کنترل‌کاراکترها/صفرعرض، نرمال‌سازی NFC، سقف طول + پیام فارسی
- `clean_username` / `clean_student_code`: الفبای محدود و الگوی مشخص
- `password_policy`: حداقل ۸ نویسه شامل حرف و رقم، بدون فاصله (اعمال‌شده در ساخت/ویرایش/بازنشانی رمز ادمین)
- `clean_int` / `clean_choice`: بازهٔ عددی و فهرست مقادیر مجاز
- `validate_image_upload`: پسوند مجاز + سقف حجم + باز شدن واقعی با Pillow (رد فایل جعلی)
- `validate_sheet_upload`: برای فایل‌های Excel/CSV ورودی گروهی
- `csv_formula_guard`: جلوگیری از CSV/Formula Injection در خروجی‌ها

### ضد Open Redirect
- `safe_redirect_target` و `redirect_back`: فقط مسیرهای داخلی هم‌میزبان؛ پارامترهای `back`/`next` کاربر هرگز مستقیم redirect نمی‌شوند (اعمال‌شده در اطلاعیه‌ها و بانک سوال)

### محدودسازی نرخ درخواست (Rate Limit)
- دکوریتور `@limit(key, max, window)` روی: ذخیرهٔ پاسخ، ذخیرهٔ دسته‌ای، آپلود/حذف تصویر پاسخ، ثبت تقلب، انتشار اطلاعیه
- پاسخ 429 برای AJAX و پیام خطا برای فرم‌ها

### امنیت نشست و هدرها
- با تغییر/بازنشانی رمز عبور، همهٔ نشست‌های فعال کاربر باطل می‌شود (`terminate_user_sessions`)
- هدر `Content-Security-Policy` + `Cross-Origin-Resource-Policy` در `SecurityHeadersMiddleware`
- `SECRET_KEY` قابل override با متغیر محیطی اختیاری `DJANGO_SECRET_KEY` (بدون اجبار؛ سیاست قبلی پروژه حفظ شده)

### قیدهای سطح دیتابیس (Migration جدید)
- `Exam`: مدت ۱ تا ۶۰۰ دقیقه؛ `end_time > start_time`
- `Question`: `max_score` بین ۰ تا ۱۰۰؛ `order >= 0`

### تست‌ها
- ۲۸ تست جدید در `core/tests.py`: پاک‌سازی متن، سیاست رمز، بازگشت امن، تزریق فرمول، اعتبارسنجی آپلود، rate limit، باطل‌سازی نشست، قیدهای مدل و ویوهای اعتبارسنجی ادمین/معلم
